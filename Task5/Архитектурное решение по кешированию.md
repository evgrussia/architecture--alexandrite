# Архитектурное решение по кешированию

## 1. Мотивация

### Проблема

MES испытывает серьёзные проблемы с производительностью:

1. **Медленная загрузка дашборда заказов.** Операторы жалуются, что первая страница MES (список заказов по статусам с фильтром и пагинацией) загружается медленно. Команда уже добавила фильтр и пагинацию, но это не помогло.

2. **Низкая скорость выполнения заказов для B2B-клиентов.** Новые клиенты, использующие API, недовольны скоростью обработки.

### Корневая причина

- БД MES (PostgreSQL) работает в единственном инстансе на чтение и запись. Каждый запрос дашборда обращается напрямую к БД.
- С линейным ростом заказов (+100/мес) нагрузка на чтение постоянно растёт — операторы постоянно обновляют дашборд, чтобы видеть новые заказы.
- Тяжёлые операции записи (расчёт стоимости, обновление статусов) конкурируют с операциями чтения на одном инстансе БД.
- Данные дашборда (список заказов по статусам) — это read-heavy workload: много операторов читают одни и те же данные, которые обновляются относительно редко.

### Что решит кеширование

- **Снижение нагрузки на БД MES** — до 80-90% запросов чтения дашборда будут обслуживаться из кеша вместо БД.
- **Ускорение загрузки дашборда** — ответ из Redis: ~1-5 мс вместо 200-2000 мс из PostgreSQL.
- **Освобождение ресурсов БД для записи** — расчёт стоимости и обновление статусов перестанут конкурировать с потоком чтения.

### Какие элементы системы планируется кешировать

| Элемент | Обоснование |
|---------|-------------|
| **Список заказов по статусам (дашборд MES)** | Основная проблема. Read-heavy: десятки операторов постоянно обновляют страницу. Данные обновляются только при смене статуса заказа. |
| **Детали заказа (карточка заказа)** | Оператор часто открывает заказ для просмотра деталей. Данные редко меняются между сменами статуса. |
| **Результат расчёта стоимости** | Расчёт занимает 2-30 мин. Результат не меняется после вычисления. Кеширование позволит мгновенно отдавать повторные запросы стоимости. |

**Не кешируем:**
- **CRM API** — внутренняя система с небольшим числом пользователей (менеджеры). Нагрузка на чтение невелика, проблемы производительности не зафиксированы.
- **Online Shop API** — данные каталога можно кешировать в перспективе, но это не является текущей проблемой. Основная нагрузка — загрузка файлов и создание заказов (запись).

## 2. Предлагаемое решение

### 2.1. Тип кеширования: серверное

Выбираем **серверное кеширование** (Redis), а не клиентское.

**Почему не клиентское:**
- Дашборд MES используется десятками операторов одновременно. При клиентском кешировании (HTTP Cache-Control, ETag) каждый браузер хранит свою копию данных, но первый запрос всё равно идёт в БД. Это не решает проблему нагрузки на БД.
- Операторам критично видеть актуальные данные — клиентский кеш может показывать устаревший список заказов, из-за чего два оператора возьмут один и тот же заказ.
- B2B API-клиенты — это серверные приложения, клиентское кеширование на их стороне неуправляемо.

**Почему серверное (Redis):**
- Один общий кеш для всех операторов — кешируем результат один раз, отдаём всем.
- Полный контроль инвалидации — при смене статуса заказа немедленно обновляем кеш.
- Redis — in-memory хранилище, время ответа ~1 мс. Managed Redis доступен в Yandex Cloud.
- Разгружает БД: запросы чтения не доходят до PostgreSQL.

### 2.2. Паттерн кеширования: Cache-Aside

Выбираем паттерн **Cache-Aside** (Lazy Loading).

**Принцип работы:**
1. Приложение проверяет, есть ли данные в Redis.
2. Если есть (cache hit) — возвращает из Redis.
3. Если нет (cache miss) — читает из БД, записывает в Redis, возвращает клиенту.
4. При изменении данных (запись) — инвалидирует соответствующий ключ в Redis.

**Почему Cache-Aside, а не другие паттерны:**

| Критерий | Cache-Aside | Write-Through | Refresh-Ahead |
|----------|-------------|---------------|---------------|
| **Описание** | Приложение управляет кешем: читает из кеша, при промахе — из БД, записывает в кеш. При записи — инвалидация кеша. | Каждая запись в БД автоматически записывается и в кеш. Чтение всегда из кеша. | Кеш автоматически обновляется до истечения TTL. Фоновый процесс подгружает данные заранее. |
| **Согласованность** | Хорошая. Инвалидация при записи обеспечивает актуальность. Кратковременное окно неконсистентности при конкурентных запросах — допустимо для дашборда. | Отличная. Кеш всегда актуален, т.к. обновляется при каждой записи. | Хорошая. Данные обновляются до истечения TTL. |
| **Сложность реализации** | **Низкая.** Простая логика: check → miss → load → cache. Один C#-разработчик может реализовать за спринт. | Средняя. Требуется обёртка над слоем записи, синхронная запись в БД + кеш. Увеличивает латентность записи. | **Высокая.** Требуется фоновый процесс обновления, предсказание какие данные скоро понадобятся. Сложная конфигурация. |
| **Нагрузка на кеш** | Оптимальная. Кешируются только запрашиваемые данные. Не засоряется неиспользуемыми ключами. | Высокая. Каждая запись дублируется в кеш, даже если данные никто не читает. | Высокая. Фоновое обновление создаёт постоянную нагрузку. |
| **Подходит для MES** | **Да.** Read-heavy workload, данные обновляются по событию (смена статуса). Простая реализация при одном C#-разработчике. | Частично. Увеличит латентность при записи (обновление статуса = запись в БД + запись в кеш). Для расчёта стоимости (2-30 мин) — overhead несущественный, но для частых обновлений статусов — нежелательно. | Нет. Невозможно предсказать, какие страницы дашборда будут запрошены (зависит от фильтров и пагинации). Избыточная сложность для текущей задачи. |

**Вывод:** Cache-Aside — оптимальный баланс между простотой реализации, согласованностью данных и производительностью для read-heavy нагрузки MES.

### 2.3. Структура ключей в Redis

```
mes:orders:status:{status}:page:{page}:size:{size}  → JSON список заказов
mes:order:{order_id}                                  → JSON деталей заказа
mes:pricing:{order_id}                                → результат расчёта стоимости
```

Примеры:
- `mes:orders:status:MANUFACTURING_STARTED:page:1:size:20` — первая страница заказов в работе.
- `mes:order:ORD-2026-00451` — детали конкретного заказа.
- `mes:pricing:ORD-2026-00451` — кешированная стоимость.

### 2.5. Стратегия инвалидации кеша

Выбираем **комбинированную стратегию: программная инвалидация + TTL** как страховка.

#### Сравнительный анализ стратегий инвалидации

| Критерий | Программная (Event-based) | Временная (TTL only) | По ключу (Manual purge) |
|----------|--------------------------|---------------------|------------------------|
| **Описание** | Кеш инвалидируется программно при каждом изменении данных (смена статуса, новый заказ). Код приложения явно удаляет/обновляет ключи в Redis. | Кеш автоматически истекает через фиксированный TTL. Данные обновляются только после истечения. | Администратор или внешний процесс вручную очищает кеш по определённым ключам. |
| **Актуальность данных** | **Высокая.** Данные обновляются мгновенно при изменении. Оператор видит новый статус заказа сразу после смены. | **Низкая.** До истечения TTL отображаются устаревшие данные. При TTL=60s оператор может до минуты видеть старый статус. | Средняя. Зависит от частоты и точности ручной очистки. |
| **Сложность** | **Средняя.** Нужно идентифицировать все точки записи и добавить инвалидацию. Для MES это конечный набор операций (смена статуса, новый заказ). | **Минимальная.** Просто выставить TTL при записи в кеш. | Высокая. Требует внешнего процесса или административного интерфейса. Не масштабируется. |
| **Риск устаревших данных** | **Минимальный.** Только при конкурентных запросах (race condition) — решается TTL-подстраховкой. | Высокий. Гарантированно устаревшие данные в пределах TTL. Критично: два оператора могут взять один заказ. | Средний. Зависит от человеческого фактора. |
| **Подходит для MES** | **Да.** Операторам критично видеть актуальные данные. Смена статуса заказа — это бизнес-событие, которое должно отражаться немедленно. | Частично. Можно использовать как дополнение (safety net), но не как основную стратегию. | Нет. Не масштабируется, зависит от ручных действий. |

#### Выбранная стратегия: программная инвалидация + TTL

**Основной механизм — программная инвалидация:**

При любом изменении данных заказа MES API выполняет:

1. Записывает изменение в БД.
2. Удаляет из Redis:
   - Ключи списков заказов по **старому** статусу (все страницы): `DEL mes:orders:status:{old_status}:*`
   - Ключи списков заказов по **новому** статусу (все страницы): `DEL mes:orders:status:{new_status}:*`
   - Ключ деталей заказа: `DEL mes:order:{order_id}`
3. Следующий запрос дашборда получит cache miss и подгрузит актуальные данные из БД.

**Страховочный механизм — TTL:**

Каждый ключ в Redis имеет TTL = 60 секунд. Это гарантирует:
- Даже если программная инвалидация не сработала (баг, сбой), данные обновятся максимум через 60 секунд.
- Защита от «вечно устаревшего» кеша при edge cases.
- 60 секунд выбрано как компромисс: достаточно короткий, чтобы не создавать проблем для операторов, достаточно длинный, чтобы снизить нагрузку на БД.

**Для результата расчёта стоимости** — отдельная логика:
- TTL = 24 часа (стоимость не меняется после расчёта).
- Инвалидация не требуется — пересчёт стоимости означает новый расчёт, который перезапишет ключ.

## 3. Дополнительное задание: сравнение двух решений

### Решение 1: Redis Cache-Aside (основное)

Описано выше. MES API проверяет Redis перед обращением к БД, инвалидирует кеш при записи.

### Решение 2: Read Replica PostgreSQL + клиентский кеш (HTTP Cache-Control)

**Описание:** Добавить read-реплику БД MES. Все запросы чтения (дашборд) направлять на реплику. Дополнительно настроить HTTP-заголовки Cache-Control с ETag для дашборда MES.

#### Сравнение

| Критерий | Решение 1: Redis Cache-Aside | Решение 2: Read Replica + HTTP Cache |
|----------|------------------------------|--------------------------------------|
| **Скорость отклика** | ~1-5 мс (in-memory). Мгновенная загрузка дашборда. | ~50-200 мс (БД на чтение, даже реплика). Заметное улучшение, но не мгновенное. |
| **Снижение нагрузки на primary БД** | Полное для кешированных запросов (80-90% запросов). | Полное для чтения — всё чтение идёт на реплику. Primary разгружается. |
| **Согласованность** | Контролируемая. Программная инвалидация + TTL 60s. | Зависит от задержки репликации (обычно <1s для PostgreSQL streaming replication). |
| **Сложность реализации** | Средняя. Изменение кода MES API (C#): добавить Redis-клиент, логику кеширования, инвалидацию. 1-2 спринта. | Низкая на стороне кода. Основная работа — DevOps: настройка реплики, роутинг запросов. Но требует разделения read/write в коде. |
| **Стоимость инфраструктуры** | Managed Redis в Yandex Cloud: ~$30-50/мес (небольшой инстанс, данные компактные). | Read replica PostgreSQL: ~$50-100/мес (инстанс БД той же спецификации). |
| **Масштабируемость** | Хорошая. Redis кластер при необходимости. | Хорошая. Можно добавить несколько реплик. |
| **Подготовка к росту** | Кеш эффективен при read-heavy. При росте записей — инвалидация чаще, но кеш всё равно полезен. | Реплика масштабирует чтение линейно. Не зависит от паттерна чтения/записи. |

### Заключение

**Рекомендуется Решение 1 (Redis Cache-Aside)** по следующим причинам:

1. **Скорость** — разница между 1-5 мс (Redis) и 50-200 мс (read replica) существенна для UX операторов, которые постоянно обновляют дашборд. Мгновенный отклик решает проблему «медленной загрузки» радикально.

2. **Эффективность для use case** — дашборд MES — это классический read-heavy, same-data workload. Десятки операторов запрашивают одни и те же списки заказов. Redis кеширует результат один раз и отдаёт всем — это эффективнее, чем каждый раз выполнять SQL-запрос (даже на реплике).

3. **Быстрая реализация** — один C#-разработчик + тимлид (бывший C#) могут реализовать за 1-2 спринта. Не требуется изменение инфраструктуры БД.

4. **Не исключает Решение 2** — в перспективе read-реплику стоит добавить для общей устойчивости системы, но как отдельную инициативу. Redis решает текущую проблему быстрее и эффективнее.
