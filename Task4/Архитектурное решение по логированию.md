# Архитектурное решение по логированию

## 1. Анализ: какие логи нужно собирать и из каких систем

### Системы, из которых требуется сбор логов

Логирование необходимо внедрить во **все** сервисы, участвующие в обработке заказов:

1. **Online Shop API** (Java Spring Boot) — точка входа B2C-заказов, загрузка 3D-моделей.
2. **MES API** (C#) — расчёт стоимости, управление производством, B2B API.
3. **CRM API** (Java Spring Boot) — подтверждение заказов, работа менеджеров.
4. **RabbitMQ** — логи брокера сообщений (системные).
5. **БД Shop / БД MES** (PostgreSQL) — slow query logs, connection errors.

### Список логов уровня INFO

#### Online Shop API

| Событие | Данные для логирования |
|---------|----------------------|
| Создание заказа (INITIATED) | `timestamp`, `order_id`, `customer_id`, `session_id`, `source=b2c` |
| Загрузка 3D-модели (FILE_UPLOADED) | `timestamp`, `order_id`, `customer_id`, `file_name`, `file_size_kb`, `upload_duration_ms` |
| Создание модели в конструкторе | `timestamp`, `order_id`, `customer_id`, `polygon_count` |
| Отправка заказа (SUBMITTED) | `timestamp`, `order_id`, `customer_id`, `items_count` |
| Отправка запроса на расчёт в MES | `timestamp`, `order_id`, `request_id`, `target_service=mes` |
| Получение результата расчёта стоимости | `timestamp`, `order_id`, `price`, `calculation_duration_ms` |
| Успешная аутентификация пользователя | `timestamp`, `customer_id`, `auth_method` |

#### MES API

| Событие | Данные для логирования |
|---------|----------------------|
| Получение заказа на расчёт | `timestamp`, `order_id`, `source` (`b2c_shop` / `b2b_api`), `polygon_count` |
| Начало расчёта стоимости | `timestamp`, `order_id`, `calculation_id`, `model_complexity` |
| Завершение расчёта (PRICE_CALCULATED) | `timestamp`, `order_id`, `calculation_id`, `price`, `duration_ms` |
| Оператор взял заказ (MANUFACTURING_STARTED) | `timestamp`, `order_id`, `operator_id` |
| Заказ выполнен (MANUFACTURING_COMPLETED) | `timestamp`, `order_id`, `operator_id`, `manufacturing_duration_ms` |
| Начало упаковки (PACKAGING) | `timestamp`, `order_id`, `operator_id` |
| Заказ отправлен (SHIPPED) | `timestamp`, `order_id`, `tracking_number` |
| Публикация сообщения в RabbitMQ | `timestamp`, `order_id`, `queue_name`, `message_type` |
| Получение сообщения из RabbitMQ | `timestamp`, `order_id`, `queue_name`, `message_type` |
| B2B API: получение запроса | `timestamp`, `order_id`, `api_key_id`, `endpoint`, `method` |

#### CRM API

| Событие | Данные для логирования |
|---------|----------------------|
| Получение заказа из MES (через RabbitMQ) | `timestamp`, `order_id`, `queue_name`, `message_type` |
| Подтверждение заказа (MANUFACTURING_APPROVED) | `timestamp`, `order_id`, `seller_id` |
| Закрытие заказа (CLOSED) | `timestamp`, `order_id`, `seller_id`, `close_reason` (`shipping_confirmed` / `manual`) |
| Публикация сообщения в RabbitMQ | `timestamp`, `order_id`, `queue_name`, `message_type` |
| Получение сообщения из RabbitMQ | `timestamp`, `order_id`, `queue_name`, `message_type` |

### Другие уровни логирования

| Уровень | Когда использовать | Примеры |
|---------|-------------------|---------|
| **DEBUG** | Детальная отладка при расследовании инцидентов. **Выключен в production по умолчанию**, включается динамически при необходимости. | Содержимое HTTP-запросов/ответов (без PII), SQL-запросы, промежуточные шаги расчёта стоимости. |
| **WARN** | Нештатные, но обрабатываемые ситуации. Система продолжает работать, но ситуация требует внимания. | Retry при отправке сообщения в RabbitMQ, медленный запрос к БД (> 1s), приближение к лимиту подключений, загрузка файла нестандартного формата. |
| **ERROR** | Ошибки, требующие реакции. Операция не выполнена. | HTTP 500, ошибка записи в БД, невозможность подключиться к RabbitMQ, таймаут расчёта стоимости, ошибка загрузки файла в S3. Логируем: `timestamp`, `order_id` (если применимо), `error_type`, `error_message`, `stack_trace`, `request_id`. |
| **FATAL** | Критические ошибки, приводящие к остановке сервиса. | OOM, невозможность подключиться к БД при старте, критическая ошибка конфигурации. |

## 2. Мотивация

### Почему нужно добавить логирование

Сейчас разбор инцидентов происходит «со слов клиента» — клиент описывает проблему менеджеру, менеджер передаёт разработчикам, и те пытаются воспроизвести ситуацию вручную. Это занимает часы и дни. После открытия B2B API количество инцидентов резко выросло, а вместе с ним и нагрузка на поддержку и разработку.

Централизованное логирование позволит:
- Быстро находить причину проблемы по `order_id` за минуты вместо часов.
- Видеть полную цепочку событий заказа через все три системы.
- Обнаруживать аномалии и атаки автоматически.
- Снизить нагрузку на разработчиков за счёт предоставления доступа к логам поддержке.

### Технические и бизнес-метрики, на которые повлияет логирование

1. **Время разбора инцидента (MTTR)** — с часов/дней до минут. Поддержка сможет самостоятельно найти в логах, что произошло с конкретным заказом, без привлечения разработчиков.

2. **Количество эскалаций от поддержки к разработчикам** — снижение на 60-70%. Поддержка получит инструмент для самостоятельной диагностики, разработчики смогут сфокусироваться на развитии продукта.

3. **Время обнаружения аномалий** — с алертингом по логам: обнаружение DDoS-атак, массовых ошибок, деградации за минуты вместо часов (когда клиенты начинают жаловаться).

4. **Процент заказов, потерянных без диагностики** — логи покажут, на каком шаге и в каком сервисе заказ «сломался». В комбинации с трейсингом это даст полную картину. Цель — 0% необъяснённых потерь.

5. **Удовлетворённость B2B-партнёров** — возможность предоставить партнёрам детальный отчёт о том, что произошло с их заказом, вместо «мы разбираемся». Прямое влияние на удержание контрактов.

### Приоритет внедрения логирования и трейсинга по системам

Команда не может внедрить всё одновременно. Порядок приоритета:

| Приоритет | Система | Обоснование |
|-----------|---------|-------------|
| **1 (первый спринт)** | **MES API** | Самая проблемная система: жалобы на медленную загрузку, точка входа B2B API, длительные расчёты стоимости, наибольшее количество переходов статусов. Именно здесь чаще всего «теряются» заказы. Один C#-разработчик + тимлид (бывший C#) могут выполнить работу. |
| **2 (второй спринт)** | **CRM API** | CRM получает заказы через RabbitMQ — это вторая по частоте точка потери заказов. Два Java-разработчика могут параллельно инструментировать CRM, пока C#-команда работает над MES. |
| **3 (третий спринт)** | **Online Shop API** | Менее критично, так как B2C-заказы создаются синхронно и сразу сохраняются в БД. Проблемы возникают позже, при передаче в MES. Но логирование здесь важно для полноты картины. |
| **4 (параллельно)** | **RabbitMQ, БД** | Системные логи RabbitMQ и PostgreSQL slow query logs — настраиваются DevOps-инженером параллельно с инструментированием API. |

## 3. Предлагаемое решение

### 3.1. Выбор технологии: стек ELK (Elasticsearch + Logstash + Kibana)

#### Архитектура

```
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  Shop API    │  │   MES API    │  │   CRM API    │
│  (Logback +  │  │  (Serilog +  │  │  (Logback +  │
│   JSON fmt)  │  │   JSON fmt)  │  │   JSON fmt)  │
└──────┬───────┘  └──────┬───────┘  └──────┬───────┘
       │                 │                 │
       │     stdout / filebeat             │
       │                 │                 │
       └────────┬────────┴────────┬────────┘
                │                 │
       ┌────────▼─────────────────▼────────┐
       │           Filebeat                │
       │   (Lightweight log shipper,       │
       │    runs on each EC2 instance)     │
       └─────────────────┬────────────────┘
                         │
                ┌────────▼────────┐
                │    Logstash     │
                │  (Parsing,     │
                │   enrichment,  │
                │   filtering)   │
                └────────┬───────┘
                         │
                ┌────────▼────────┐
                │  Elasticsearch  │
                │  (Storage &     │
                │   indexing)     │
                └────────┬───────┘
                         │
                ┌────────▼────────┐
                │     Kibana      │
                │  (UI, search,   │
                │   dashboards,   │
                │   alerting)     │
                └─────────────────┘
```

#### Компоненты для внедрения

**Новые компоненты:**

1. **Filebeat** — устанавливается на каждом EC2-инстансе как sidecar-агент. Собирает логи из stdout/файлов приложений и отправляет в Logstash. Лёгкий, минимальный overhead.

2. **Logstash** — отдельный EC2-инстанс. Принимает логи от Filebeat, парсит JSON, обогащает метаданными (имя сервиса, окружение), фильтрует чувствительные данные, отправляет в Elasticsearch.

3. **Elasticsearch** — Managed Elasticsearch в Yandex Cloud. Хранилище и поисковый движок для логов. Индексирование по `timestamp`, `order_id`, `service_name`, `level`.

4. **Kibana** — UI для поиска, визуализации и анализа логов. Доступ через корпоративный reverse proxy.

**Доработка существующих компонентов:**

5. **Online Shop API / CRM API** (Java Spring Boot) — настроить Logback с JSON-форматом вывода (logback-json-layout). Обеспечить структурированное логирование с обязательными полями: `timestamp`, `level`, `service`, `order_id`, `trace_id`, `span_id`, `message`.

6. **MES API** (C#) — настроить Serilog с JSON-форматом. Аналогичная структура полей. Обеспечить корреляцию с `trace_id` из OpenTelemetry.

#### Обновлённая C4-диаграмма

> Компоненты для отображения на схеме (выделить красным):
> - Filebeat (на каждом EC2 с API-сервисом)
> - Logstash (отдельный контейнер)
> - Elasticsearch (отдельный контейнер / Managed Service)
> - Kibana (отдельный контейнер)
> - Связи: Shop API → Filebeat → Logstash → Elasticsearch → Kibana
> - Связи: CRM API → Filebeat → Logstash
> - Связи: MES API → Filebeat → Logstash
>
> **[Диаграмма: Task4/c4_logging.drawio](c4_logging.drawio)**

### 3.2. Формат логов

Все сервисы должны писать логи в **структурированном JSON-формате**:

```json
{
  "timestamp": "2026-03-21T14:32:15.123Z",
  "level": "INFO",
  "service": "mes-api",
  "environment": "prod",
  "trace_id": "abc123def456",
  "span_id": "789ghi",
  "order_id": "ORD-2026-00451",
  "customer_id_hash": "sha256:a1b2c3...",
  "message": "Order status changed",
  "details": {
    "status_from": "SUBMITTED",
    "status_to": "PRICE_CALCULATED",
    "price": 45000,
    "duration_ms": 180000
  }
}
```

Ключевые поля:
- `trace_id` / `span_id` — корреляция с трейсингом (OpenTelemetry).
- `order_id` — быстрый поиск всех событий заказа.
- `customer_id_hash` — хеш вместо открытого ID для безопасности.

### 3.3. Политика безопасности

#### Работа с чувствительными данными

- **Запрет логирования PII:** Имена, email, телефоны, адреса, номера карт **никогда** не записываются в логи.
- **Хеширование идентификаторов клиентов:** `customer_id` логируется в виде SHA-256 хеша. Маппинг hash → real_id доступен только через CRM с соответствующими правами.
- **Маскирование в Logstash:** Настроить filter-плагин для автоматического обнаружения и маскирования паттернов PII (email, телефон), если они случайно попали в лог.
- **API-ключи B2B-партнёров:** Логировать только `api_key_id` (идентификатор), никогда не логировать сам ключ.
- **Stack traces:** Допустимы в уровне ERROR, но не должны содержать пользовательских данных в переменных.

#### Контроль доступа

| Роль | Доступ к Kibana | Что видит |
|------|----------------|-----------|
| **Поддержка** | Read-only, фильтр по `level ≥ INFO` | Логи INFO и выше. Поиск по `order_id`. Не видит DEBUG-логи и stack traces. |
| **Разработчик** | Read-only, все уровни | Все логи включая DEBUG (когда включён) и ERROR с stack traces. |
| **Тимлид / Архитектор** | Read-only + dashboards | Все логи + аналитические дашборды. |
| **DevOps** | Администратор | Управление индексами, политиками хранения, настройками Kibana. |
| **Продакт-менеджер** | Read-only, только дашборды | Агрегированные метрики из логов (количество заказов, ошибок). Без доступа к сырым логам. |

Аутентификация — через корпоративную SSO (OAuth2 Proxy перед Kibana). Kibana недоступна из интернета — только через VPN или internal reverse proxy.

### 3.4. Политика хранения логов

#### Индексация

Логи разделяются по **отдельным индексам на каждую систему и окружение**:

| Индекс | Описание |
|--------|----------|
| `logs-shop-api-prod-YYYY.MM` | Логи Online Shop API, production |
| `logs-crm-api-prod-YYYY.MM` | Логи CRM API, production |
| `logs-mes-api-prod-YYYY.MM` | Логи MES API, production |
| `logs-rabbitmq-prod-YYYY.MM` | Системные логи RabbitMQ |
| `logs-*-dev-YYYY.MM` | Логи dev-окружения (общий шаблон) |
| `logs-*-release-YYYY.MM` | Логи release-окружения |

Ротация индексов — ежемесячная (по дате в имени индекса).

#### Сроки хранения

| Tier | Срок | Тип хранения | Описание |
|------|------|-------------|----------|
| **Hot** | 14 дней | SSD | Активный поиск и анализ. Основная рабочая зона для поддержки и разработчиков. |
| **Warm** | 90 дней | HDD | Исторический анализ. Запросы медленнее, но данные доступны. |
| **Cold / Delete** | После 90 дней | Удаление (или архив в S3) | Для compliance можно архивировать в S3 Glacier. По умолчанию — удаление. |
| **Dev/Release** | 7 дней | SSD | Логи тестовых окружений хранятся недолго — нужны только для отладки. |

#### Оценка объёма

| Система | Среднее кол-во событий/день | Средний размер события | Объём/день | Объём/месяц |
|---------|---------------------------|----------------------|------------|-------------|
| Shop API | ~50,000 | ~0.5 KB | ~25 MB | ~750 MB |
| MES API | ~100,000 (с B2B API) | ~0.6 KB | ~60 MB | ~1.8 GB |
| CRM API | ~30,000 | ~0.5 KB | ~15 MB | ~450 MB |
| RabbitMQ | ~20,000 | ~0.3 KB | ~6 MB | ~180 MB |
| **Итого** | **~200,000** | | **~106 MB** | **~3.2 GB** |

С учётом линейного роста (+100 заказов/месяц) и индексации Elasticsearch (overhead ~1.5x) через полгода: ~6-8 GB/месяц. Hot + Warm (104 дня) ≈ 25-35 GB. Это скромный объём для Managed Elasticsearch.

## 4. От сбора логов к анализу логов

### 4.1. Алертинг

Да, алертинг необходим. Настраиваем через **Kibana Alerting** (Watcher) или интегрируем с Prometheus Alertmanager (из задания 3):

| Алерт | Условие | Реакция |
|-------|---------|---------|
| **Всплеск ERROR** | Более 50 записей уровня ERROR за 5 минут в любом сервисе | Slack-уведомление в `#alerts`. Дежурный инженер проверяет Kibana. |
| **Аномальный рост создания заказов** | Количество событий `order_created` за минуту превышает 3x от скользящего среднего за последний час | Slack-уведомление. Возможная DDoS-атака или бот-активность. Рассмотреть включение rate limiting. |
| **Рост DLQ-сообщений** | Появление ERROR-логов с `message_type=dlq` | Критический алерт. PagerDuty. Заказы теряются. |
| **Массовые таймауты расчёта** | Более 10 логов `pricing_calculation_timeout` за 30 минут | Уведомление дежурного + оператора MES. MES перегружена. |
| **Ошибки подключения к БД** | ERROR-логи с `error_type=db_connection` | Критический алерт. PagerDuty. Возможна деградация или недоступность БД. |
| **B2B API: массовые ошибки** | Error rate > 5% для запросов с `source=b2b_api` за 10 минут | Уведомление дежурного + менеджера B2B-аккаунтов. |

### 4.2. Обнаружение аномалий

Да, поиск аномалий необходим. Реализация в два этапа:

**Этап 1 (правила):** Статические правила в Kibana Alerting (описаны выше). Покрывают известные сценарии: всплески ошибок, аномальный трафик, таймауты.

**Этап 2 (Machine Learning):** Elasticsearch ML (X-Pack) для обнаружения аномалий:
- **Anomaly Detection Job** на количество создания заказов — обнаружит нетипичные паттерны (DDoS, бот-активность) без статических порогов.
- **Anomaly Detection Job** на error rate по сервисам — обнаружит деградацию, не попадающую под фиксированные пороги.
- **Rare events detection** — обнаружение редких, ранее не встречавшихся типов ошибок.

### 4.3. Дашборды для анализа

| Дашборд | Содержание | Аудитория |
|---------|-----------|-----------|
| **Order Flow** | Количество заказов по статусам за период, время переходов между статусами, «зависшие» заказы | Поддержка, продакт |
| **Error Analysis** | Top-10 ошибок, error rate по сервисам, тренды | Разработчики |
| **B2B API Health** | RPS, error rate, latency по B2B-партнёрам | Менеджеры, разработчики |
| **System Health** | Количество логов по уровням, аномалии, алерты | DevOps, тимлид |

## 5. Критерии выбора технологии и обоснование (дополнительное задание)

### Критерии

| # | Критерий | Вес | Описание |
|---|----------|-----|----------|
| 1 | **Полнотекстовый поиск** | Высокий | Возможность быстро искать по `order_id`, `error_message`, произвольному тексту в логах. Ключевой use case — поддержка ищет конкретный заказ. |
| 2 | **Масштабируемость** | Высокий | Способность справляться с растущим объёмом логов при линейном росте заказов (+100/мес) и возможном подключении новых B2B-партнёров. |
| 3 | **Экосистема и совместимость** | Высокий | Поддержка Java (Spring Boot) и C# (ASP.NET), интеграция с OpenTelemetry (trace_id), наличие агентов для сбора логов. |
| 4 | **Стоимость владения (TCO)** | Средний | Лицензионные расходы, стоимость инфраструктуры, стоимость поддержки. С учётом небольшой команды (1 DevOps) — важна простота эксплуатации. |
| 5 | **Визуализация и алертинг** | Средний | Встроенные возможности для дашбордов, алертинга и обнаружения аномалий. Команде не нужно интегрировать отдельные инструменты. |
| 6 | **Политики хранения** | Средний | Поддержка tiered storage (hot/warm/cold), автоматическая ротация индексов, управление жизненным циклом данных. |
| 7 | **Кривая обучения** | Низкий | Насколько быстро команда (в т.ч. поддержка) сможет начать использовать инструмент. |

### Сравнение технологий

| Критерий | ELK (Elasticsearch + Logstash + Kibana) | Grafana Loki + Grafana | Yandex Cloud Logging |
|----------|----------------------------------------|----------------------|---------------------|
| **Полнотекстовый поиск** | **Отлично.** Elasticsearch — лучший полнотекстовый движок. Поиск по любому полю, сложные запросы, агрегации. | Слабо. Loki индексирует только ярлыки, не содержимое логов. Поиск по тексту — через grep, медленно на больших объёмах. | Средне. Базовый поиск, ограниченные возможности фильтрации. |
| **Масштабируемость** | **Отлично.** Горизонтальное масштабирование, шардирование, реплики. Proven at scale (Netflix, Uber). | Хорошо. Компактное хранение, меньше ресурсов, но ограничения при сложных запросах. | Хорошо. Managed service, масштабируется автоматически. |
| **Экосистема** | **Отлично.** Logback (Java), Serilog (C#), Filebeat, OpenTelemetry integration. Огромное сообщество. | Хорошо. Promtail/Grafana Agent, OTel support. Меньше готовых интеграций для C#. | Средне. Yandex-специфичные агенты, ограниченная экосистема. |
| **TCO** | Средне. Open-source, но Elasticsearch требует ресурсов (RAM, SSD). Managed ES в Yandex Cloud упрощает, но стоит дороже. | **Отлично.** Минимальные ресурсы, компактное хранение. Самое дешёвое решение. | Хорошо. Pay-per-use, нет расходов на инфраструктуру. Но vendor lock-in. |
| **Визуализация и алертинг** | **Отлично.** Kibana — мощная визуализация, встроенный алертинг, ML для аномалий. | Хорошо. Grafana — сильная визуализация, но алертинг по логам слабее. | Слабо. Минимальные дашборды, базовый алертинг. |
| **Политики хранения** | **Отлично.** Index Lifecycle Management (ILM): hot → warm → cold → delete. Гибкая настройка. | Хорошо. Retention policies, но проще и менее гибко. | Средне. Ограниченные настройки retention. |
| **Кривая обучения** | Средне. KQL (Kibana Query Language) нужно изучить, но он интуитивен. Много документации. | Хорошо. LogQL проще. Если команда уже использует Grafana для метрик — единый интерфейс. | **Отлично.** Минимальная настройка, managed service. |

### Выбор: ELK

**Обоснование:**

ELK выбран как основное решение по следующим причинам:

1. **Полнотекстовый поиск** — ключевое требование. Поддержка должна мгновенно находить все события по `order_id`. Loki принципиально не поддерживает полнотекстовый поиск — это архитектурное ограничение, которое нельзя обойти.

2. **Elasticsearch уже используется для трейсинга** (Jaeger backend из Задания 3). Переиспользование инфраструктуры снижает TCO и упрощает эксплуатацию. Один DevOps-инженер управляет одним кластером, а не двумя системами.

3. **ML для аномалий** — встроенный в Elasticsearch, не требует отдельных инструментов. Для обнаружения DDoS и аномальных паттернов это критично.

4. **Зрелость экосистемы** — максимальная поддержка и Java (Logback), и C# (Serilog). Команде не придётся писать кастомные интеграции.

5. **Компромисс по TCO** — ELK дороже Loki, но использование Managed Elasticsearch в Yandex Cloud снижает операционные расходы. С объёмом логов ~3-8 GB/месяц стоимость будет скромной.
