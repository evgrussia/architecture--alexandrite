# Выбор и настройка мониторинга в системе

## 1. Мотивация

### Почему нужен мониторинг

Сейчас единственный источник данных о работе системы — Яндекс Метрика, которая покрывает только поведение пользователей на сайте интернет-магазина. После открытия API для внешних продавцов (B2B) значительная часть трафика стала поступать в обход сайта. Это означает, что у команды нет видимости в:

- **Работу API** — сколько запросов приходит от B2B-партнёров, какой процент завершается ошибками, какова латентность.
- **Состояние внутренних сервисов** — загруженность MES, CRM, состояние очередей RabbitMQ.
- **Инфраструктуру** — нагрузка на базы данных, потребление CPU/Memory, заполняемость хранилищ.

Компания теряет крупные контракты из-за проблем с заказами, но команда узнаёт о сбоях только от клиентов. Время реакции на инцидент — часы и дни вместо минут.

### Что мониторинг даст компании

1. **Снижение времени обнаружения инцидентов** — с часов/дней (когда клиент пожалуется) до минут (автоматический алерт). Это напрямую влияет на количество потерянных заказов.
2. **Данные для принятия решений** — понимание реальной нагрузки, узких мест и трендов позволит обоснованно планировать масштабирование и распределять ресурсы команды.
3. **Сохранение B2B-контрактов** — возможность предоставить партнёрам SLA, подкреплённый реальными метриками, и проактивно решать проблемы до эскалации.
4. **Снижение нагрузки на поддержку** — вместо ручного разбора «со слов клиента» команда сможет быстро видеть состояние конкретного сервиса и очереди.
5. **Capacity planning** — данные о трендах потребления ресурсов позволят планировать масштабирование заранее, а не реактивно после сбоя.

## 2. Выбор подхода к мониторингу

Для разных частей системы используются разные подходы:

### API-сервисы (Online Shop API, CRM API, MES API) — метод RED

**RED** (Rate, Errors, Duration) — наиболее подходящий метод для мониторинга request-driven сервисов. Все три API-сервиса обслуживают синхронные HTTP-запросы, поэтому RED даёт наиболее полезную картину их здоровья:

- **Rate** — количество запросов в секунду (RPS). Показывает текущую нагрузку и позволяет обнаружить аномалии (резкий рост или падение трафика).
- **Errors** — количество и доля ошибок. Показывает качество обслуживания.
- **Duration** — время ответа. Показывает, как быстро сервис обрабатывает запросы.

### Инфраструктура (БД, EC2-инстансы, S3) — метод USE

**USE** (Utilization, Saturation, Errors) — оптимальный метод для мониторинга инфраструктурных ресурсов. Он позволяет понять, насколько ресурс загружен, есть ли очередь ожидающих запросов и возникают ли ошибки:

- **Utilization** — процент использования ресурса (CPU, Memory, Disk, Connections).
- **Saturation** — наличие очереди или отложенной работы (ожидающие соединения к БД, swap usage).
- **Errors** — ошибки ресурса (failed connections, OOM events).

### Очередь сообщений (RabbitMQ) — «Четыре золотых сигнала»

Для RabbitMQ применяем **«Четыре золотых сигнала»** (Latency, Traffic, Errors, Saturation), так как это компонент с двойной природой — он и обрабатывает запросы (публикация/потребление сообщений), и является инфраструктурным ресурсом:

- **Latency** — время от публикации сообщения до его потребления.
- **Traffic** — количество сообщений в единицу времени.
- **Errors** — сообщения в DLQ, ошибки подключения.
- **Saturation** — глубина очередей, количество сообщений в обработке (in-flight).

## 3. Метрики для отслеживания

### 3.1. RabbitMQ

#### Number of dead-letter-exchange letters in RabbitMQ
- **Зачем:** Сообщения в DLQ — это заказы, которые не были обработаны. Каждое такое сообщение потенциально означает потерянный заказ. Рост DLQ — прямой индикатор проблемы с обработкой заказов, что является основной бизнес-проблемой компании.
- **Ярлыки:**
  - `queue` — имя исходной очереди (для определения, между какими системами произошёл сбой, например `mes-to-crm`, `shop-to-mes`)
  - `reason` — причина попадания в DLQ (`rejected`, `expired`, `max-retries-exceeded`)

#### Number of messages in flight in RabbitMQ
- **Зачем:** Показывает количество сообщений, которые были доставлены потребителю, но ещё не подтверждены (unacked). Высокое значение указывает на то, что потребитель не справляется с нагрузкой — сообщения «зависают». Это ранний индикатор проблемы до того, как заказы начнут теряться.
- **Ярлыки:**
  - `queue` — имя очереди (`orders-pricing`, `orders-approval`, `orders-status-update`)
  - `consumer` — идентификатор потребителя

### 3.2. API-сервисы — Rate (RPS)

#### Number of requests (RPS) for internet shop API
- **Зачем:** Базовый показатель нагрузки на основной канал продаж (B2C). Позволяет обнаружить аномальный рост (DDoS, ботов) или падение (сбой на стороне фронтенда). С учётом линейного роста на 100 заказов/месяц критично понимать текущий уровень трафика для планирования масштабирования.
- **Ярлыки:**
  - `method` — HTTP-метод (`GET`, `POST`, `PUT`)
  - `endpoint` — путь API (`/orders`, `/products`, `/upload`)
  - `status_code` — код ответа (для разделения успешных и ошибочных)

#### Number of requests (RPS) for CRM API
- **Зачем:** CRM — ключевая система для менеджеров по продажам. Мониторинг RPS позволит понимать нагрузку со стороны внутренних пользователей и обнаруживать проблемы доступности.
- **Ярлыки:**
  - `method` — HTTP-метод
  - `endpoint` — путь API
  - `status_code` — код ответа

#### Number of requests (RPS) for MES API
- **Зачем:** MES обрабатывает ключевые операции: расчёт стоимости, обновление статусов заказов. Также MES API используется внешними B2B-клиентами. Мониторинг RPS критичен для понимания нагрузки и обеспечения SLA для партнёров.
- **Ярлыки:**
  - `method` — HTTP-метод
  - `endpoint` — путь API (`/orders`, `/pricing`, `/status`)
  - `status_code` — код ответа
  - `source` — источник запроса (`internal`, `b2b_api`)

#### Number of requests (RPS) per user for internet shop API
- **Зачем:** Выявление аномальной активности конкретных пользователей (боты, парсинг, злоупотребление). Необходима для будущего rate limiting.
- **Ярлыки:**
  - `user_id` — идентификатор пользователя
  - `endpoint` — путь API

#### Number of requests (RPS) per user for MES API
- **Зачем:** Критично для B2B-сценария — позволяет контролировать потребление API внешними партнёрами, выявлять злоупотребления и обосновывать квоты.
- **Ярлыки:**
  - `user_id` / `api_key` — идентификатор партнёра
  - `endpoint` — путь API

> **Примечание:** RPS per user для CRM API не включаем, так как CRM используется ограниченным числом внутренних сотрудников, аномальная активность маловероятна.

### 3.3. API-сервисы — Errors

#### Number of HTTP 500 for shop API
- **Зачем:** Серверные ошибки 500 — это необработанные сбои, означающие, что пользователь не смог выполнить действие (создать заказ, загрузить модель). Каждая 500-ошибка потенциально означает потерянный заказ или клиента.
- **Ярлыки:**
  - `endpoint` — путь API
  - `method` — HTTP-метод
  - `error_type` — тип исключения (если доступен)

#### Number of HTTP 500 for CRM API
- **Зачем:** Ошибки в CRM блокируют работу менеджеров по продажам — они не могут подтвердить заказы, обновить статусы, работать с клиентами.
- **Ярлыки:**
  - `endpoint` — путь API
  - `method` — HTTP-метод

#### Number of HTTP 500 for MES API
- **Зачем:** Ошибки MES API критичны вдвойне: они влияют и на внутренних операторов, и на B2B-партнёров. Ошибка при расчёте стоимости или обновлении статуса может привести к зависанию заказа.
- **Ярлыки:**
  - `endpoint` — путь API
  - `method` — HTTP-метод
  - `source` — источник запроса (`internal`, `b2b_api`)

#### Number of HTTP 200 for shop API / CRM API / MES API
- **Зачем:** В сочетании с HTTP 500 позволяет вычислить **error rate** (процент ошибок), что является более информативным показателем, чем абсолютное число ошибок. Error rate 1% при 1000 RPS и при 10 RPS — принципиально разные ситуации.
- **Ярлыки:** аналогичны ярлыкам HTTP 500 для соответствующего сервиса.

### 3.4. API-сервисы — Duration (Latency)

#### Response time (latency) for shop API
- **Зачем:** Высокая латентность напрямую влияет на конверсию интернет-магазина. Медленный API — пользователи уходят, не завершив заказ. Необходимо отслеживать перцентили (p50, p95, p99), а не только среднее.
- **Ярлыки:**
  - `endpoint` — путь API
  - `method` — HTTP-метод

#### Response time (latency) for CRM API
- **Зачем:** Медленный CRM снижает продуктивность менеджеров, задерживает подтверждение заказов.
- **Ярлыки:**
  - `endpoint` — путь API
  - `method` — HTTP-метод

#### Response time (latency) for MES API
- **Зачем:** Именно MES является проблемным компонентом с жалобами на медленную загрузку дашборда. Мониторинг латентности позволит количественно измерить проблему и отслеживать эффект от оптимизаций (кеширование, read-реплики).
- **Ярлыки:**
  - `endpoint` — путь API (критично отдельно отслеживать `/dashboard` / список заказов)
  - `method` — HTTP-метод
  - `source` — `internal` / `b2b_api`

### 3.5. Инфраструктура — Utilization

#### CPU % for shop API / CRM API / MES API
- **Зачем:** Показатель загруженности вычислительных ресурсов. При приближении к 100% сервис начинает деградировать — увеличивается латентность, появляются таймауты. С учётом линейного роста нагрузки критично отслеживать тренд потребления CPU для своевременного масштабирования.
- **Ярлыки:**
  - `instance_id` — идентификатор EC2-инстанса
  - `service` — название сервиса (`shop`, `crm`, `mes`)

#### Memory Utilisation for shop API / CRM API / MES API
- **Зачем:** Утечки памяти — распространённая проблема в Java (shop, CRM) и C# (MES) приложениях. Постепенный рост потребления памяти без освобождения приведёт к OOM и падению сервиса. Особенно важно для MES, который обрабатывает тяжёлые 3D-модели.
- **Ярлыки:**
  - `instance_id` — идентификатор EC2-инстанса
  - `service` — название сервиса

#### Memory Utilisation for shop db instance / MES db instance
- **Зачем:** Недостаток памяти для БД означает, что данные не помещаются в кеш (buffer pool), и запросы начинают читать с диска — это катастрофическое падение производительности. Для MES db это особенно критично, учитывая жалобы на медленный дашборд.
- **Ярлыки:**
  - `instance_id` — идентификатор инстанса БД
  - `database` — имя базы (`shop_db`, `mes_db`)

#### Number of connections for shop db instance / MES db instance
- **Зачем:** Базы данных имеют ограничение на максимальное количество подключений. При достижении лимита новые запросы будут отклоняться, что приведёт к 500-ошибкам на уровне API. С учётом планов на масштабирование (несколько инстансов API) количество подключений будет расти.
- **Ярлыки:**
  - `instance_id` — идентификатор инстанса БД
  - `database` — имя базы
  - `state` — состояние подключения (`active`, `idle`, `waiting`)

#### Size of shop db instance / MES db instance
- **Зачем:** Контроль роста объёма данных. При достижении лимита диска БД перестанет записывать данные — это полная остановка работы. С линейным ростом заказов (100/месяц) и хранением 3D-моделей размер базы будет расти предсказуемо, но его нужно отслеживать.
- **Ярлыки:**
  - `instance_id` — идентификатор инстанса БД
  - `database` — имя базы

#### Size of S3 storage
- **Зачем:** S3 используется для хранения 3D-моделей. С ростом заказов объём хранилища растёт. Хотя S3 масштабируется автоматически, стоимость хранения растёт, и бизнесу важно понимать этот тренд для бюджетирования.
- **Ярлыки:**
  - `bucket` — имя бакета

### 3.6. API-сервисы — Traffic (дополнительные метрики)

#### Kb transferred (received) for shop API / MES API
- **Зачем:** Пользователи загружают 3D-модели, которые могут быть большого размера. Мониторинг входящего трафика позволит выявить аномально большие загрузки, которые могут перегрузить систему, а также планировать пропускную способность сети.
- **Ярлыки:**
  - `endpoint` — путь API
  - `source` — `internal` / `b2b_api` (для MES)

#### Kb provided (sent) for shop API / MES API
- **Зачем:** Большой исходящий трафик может указывать на неоптимальные ответы API (избыточные данные) или массовую выгрузку данных. Для дашборда MES — позволит понять, не возвращается ли избыточный объём данных.
- **Ярлыки:**
  - `endpoint` — путь API

> **Примечание:** Для CRM API метрики трафика (Kb received/sent) не включаем в первую очередь, так как CRM работает с текстовыми данными небольшого объёма и имеет ограниченное число пользователей.

### 3.7. Sessions

#### Number of simultaneous sessions for shop API
- **Зачем:** Показывает количество одновременных пользователей. Позволяет коррелировать нагрузку с количеством пользователей, обнаруживать аномальный рост (бот-атаки), планировать ёмкость.
- **Ярлыки:**
  - `type` — тип сессии (`authenticated`, `anonymous`)

#### Number of simultaneous sessions for MES API
- **Зачем:** Для MES важно отслеживать, сколько операторов одновременно работает с системой. Это позволит коррелировать жалобы на медленную загрузку с количеством одновременных пользователей.
- **Ярлыки:**
  - `source` — `internal` / `b2b_api`

> **Примечание:** Сессии CRM API не приоритетны — количество менеджеров стабильно и невелико.

### 3.8. Дополнительные метрики (не из списка)

#### Order processing time (время обработки заказа по этапам)
- **Зачем:** Бизнес-метрика, которая покажет, сколько времени заказ проводит в каждом статусе. Позволит обнаружить «зависания» и обосновать необходимость оптимизаций.
- **Ярлыки:**
  - `from_status` — начальный статус
  - `to_status` — конечный статус
  - `order_source` — `b2c` / `b2b`

#### RabbitMQ queue depth (количество сообщений в очереди)
- **Зачем:** В отличие от in-flight (unacked), показывает общее количество сообщений, ожидающих обработки. Растущая очередь — признак того, что потребитель не справляется.
- **Ярлыки:**
  - `queue` — имя очереди

#### Error rate (%) per service
- **Зачем:** Вычисляемая метрика (HTTP 500 / (HTTP 200 + HTTP 500) * 100%). Более информативна, чем абсолютные числа. Позволяет установить SLO (например, error rate < 1%).
- **Ярлыки:**
  - `service` — название сервиса
  - `endpoint` — путь API

## 4. Показатели насыщенности (Saturation)

### Пороговые значения и реакции

| Метрика | Warning (предупреждение) | Critical (критический) | Действие при Warning | Действие при Critical |
|---------|-------------------------|----------------------|---------------------|----------------------|
| **CPU % (API-сервисы)** | > 70% в течение 5 мин | > 90% в течение 2 мин | Создать тикет на масштабирование. Уведомление в Slack-канал команды. | Автоматическое добавление инстанса (autoscaling). Уведомление дежурного инженера (PagerDuty/звонок). |
| **Memory Utilisation (API-сервисы)** | > 80% в течение 10 мин | > 95% в течение 2 мин | Создать тикет на анализ утечек памяти. Уведомление в Slack. | Автоматический рестарт инстанса. Уведомление дежурного (PagerDuty). |
| **Memory Utilisation (БД)** | > 80% | > 90% | Создать тикет на увеличение инстанса БД. Уведомление DevOps. | Уведомление дежурного инженера (PagerDuty/звонок). Эскалация на тимлида. |
| **DB Connections (БД)** | > 80% от max_connections | > 95% от max_connections | Создать тикет. Проверить наличие connection leaks. | Уведомление дежурного (PagerDuty). Перезапуск пулов соединений. |
| **DB Size (БД)** | > 80% от выделенного диска | > 90% от выделенного диска | Создать тикет на расширение хранилища. Уведомление DevOps. | Немедленное расширение диска. Уведомление дежурного + тимлида. |
| **RabbitMQ DLQ** | > 0 сообщений | > 10 сообщений за 10 мин | Создать тикет на разбор. Уведомление в Slack. | Уведомление дежурного (PagerDuty/звонок). Расследование потери заказов. |
| **RabbitMQ queue depth** | > 1000 сообщений | > 5000 сообщений | Создать тикет. Проверить потребителей. | Уведомление дежурного. Масштабирование потребителей. |
| **Error rate (API)** | > 1% в течение 5 мин | > 5% в течение 2 мин | Создать тикет. Уведомление в Slack. | Уведомление дежурного (PagerDuty/звонок). Немедленное расследование. |
| **Latency p95 (shop API)** | > 500ms в течение 5 мин | > 2s в течение 2 мин | Создать тикет на оптимизацию. Уведомление в Slack. | Уведомление дежурного. Проверка состояния БД и зависимостей. |
| **Latency p95 (MES API)** | > 1s в течение 5 мин | > 5s в течение 2 мин | Создать тикет. Уведомление в Slack. | Уведомление дежурного. Проверка состояния БД MES. |
| **S3 storage size** | > 80% от бюджетного лимита | > 95% от бюджетного лимита | Уведомление продакт-менеджера о росте расходов. | Уведомление руководства. Анализ политики хранения. |

### Обоснование пороговых значений

- **CPU 70%/90%** — при 70% ещё есть запас для обработки пиковых нагрузок; при 90% система на грани и любой пик вызовет деградацию. Значения стандартные для облачных инстансов.
- **Memory 80%/95%** — базы данных и JVM/CLR активно используют память для кеширования; при 95% начнётся swap или OOM.
- **DB Connections 80%/95%** — пулы соединений должны иметь запас; исчерпание соединений = полная остановка обработки запросов.
- **DLQ > 0** — любое сообщение в DLQ означает необработанный заказ; для «Александрита» каждый потерянный заказ — это потеря клиента.
- **Error rate 1%/5%** — 1% является индустриальным стандартом для SLO; 5% означает серьёзную деградацию сервиса.

## 5. План действий

### Этап 1. Развёртывание инфраструктуры мониторинга (1-2 недели)

1. **Развернуть Prometheus** как time-series базу данных для сбора метрик. Использовать Managed Prometheus в Yandex Cloud (или развернуть на отдельном EC2-инстансе).
2. **Развернуть Grafana** для визуализации метрик и создания дашбордов. Использовать Managed Grafana или развернуть на EC2.
3. **Настроить Alertmanager** для маршрутизации алертов. Интегрировать со Slack (канал `#alerts`) и PagerDuty (или аналогом) для критических уведомлений.
4. **Настроить RabbitMQ Management Plugin** и экспортёр метрик для Prometheus (`rabbitmq_exporter`).

### Этап 2. Инструментирование API-сервисов (2-3 недели)

5. **Добавить Micrometer (Java) в Online Shop API и CRM API** — библиотека автоматически экспортирует метрики HTTP-запросов (RPS, latency, status codes) в формате Prometheus.
6. **Добавить prometheus-net (C#) в MES API** — аналогичная библиотека для .NET-экосистемы.
7. **Настроить кастомные метрики** — order processing time, бизнес-метрики по статусам заказов.
8. **Настроить Node Exporter** на всех EC2-инстансах для сбора метрик CPU, Memory, Disk, Network.

### Этап 3. Инструментирование баз данных и хранилищ (1 неделя)

9. **Настроить мониторинг Managed БД** через Yandex Cloud Monitoring API или PostgreSQL/MySQL exporter.
10. **Настроить мониторинг S3** через CloudWatch-совместимые метрики Yandex Cloud.

### Этап 4. Создание дашбордов и алертов (1-2 недели)

11. **Создать дашборд "System Overview"** — общее здоровье системы (error rate, latency, RPS по всем сервисам).
12. **Создать дашборд "RabbitMQ"** — состояние очередей, DLQ, in-flight сообщения.
13. **Создать дашборд "Infrastructure"** — CPU, Memory, Disk, Connections по всем инстансам.
14. **Создать дашборд "Business Metrics"** — время обработки заказов по этапам, количество заказов по статусам.
15. **Настроить алерты** согласно таблице пороговых значений из раздела 4.
16. **Настроить дежурства** — определить расписание on-call для инженеров, эскалационные цепочки.

### Этап 5. Верификация и документирование (1 неделя)

17. **Провести тестирование алертов** — убедиться, что уведомления приходят корректно.
18. **Создать runbook** — для каждого алерта описать шаги диагностики и устранения.
19. **Обучить команду** — провести демонстрацию дашбордов и процедуры реагирования на алерты.
