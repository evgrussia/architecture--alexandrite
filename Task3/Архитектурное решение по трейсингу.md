# Архитектурное решение по трейсингу

## 1. Анализ системы: где заказ может «сломаться» или зависнуть

### Системы, которые необходимо покрыть трейсингом

Трейсингом необходимо покрыть все системы, участвующие в жизненном цикле заказа:

1. **Online Shop API** (Java Spring Boot) — точка входа заказа для B2C-клиентов.
2. **MES API** (C#) — расчёт стоимости, производство, упаковка, отгрузка. Также точка входа для B2B-клиентов через API.
3. **CRM API** (Java Spring Boot) — подтверждение заказа, закрытие заказа.
4. **RabbitMQ** — асинхронная связь между MES и CRM.
5. **База данных MES** — хранение данных о заказах, статусах, расчётах.
6. **База данных Online Shop** — хранение данных о заказах, пользователях, файлах.
7. **S3-хранилище** — загрузка и хранение 3D-моделей.

### Точки, где заказ может «сломаться» или зависнуть

| # | Точка отказа | Переход статуса | Описание проблемы |
|---|-------------|----------------|-------------------|
| 1 | Online Shop → S3 | INITIATED → FILE_UPLOADED | Ошибка загрузки 3D-модели: таймаут, превышение размера, сетевой сбой. Заказ остаётся в статусе INITIATED навсегда. |
| 2 | Online Shop → MES (HTTP/Queue) | SUBMITTED → PRICE_CALCULATED | Запрос на расчёт стоимости не доходит до MES или MES не отвечает. Расчёт сложной модели может занимать до 30 минут — не ясно, заказ обрабатывается или завис. |
| 3 | MES → RabbitMQ → CRM | PRICE_CALCULATED → MANUFACTURING_APPROVED | Сообщение о рассчитанной стоимости теряется в очереди или не доставляется в CRM. Заказ завис в MES, CRM о нём не знает. |
| 4 | CRM → RabbitMQ → MES | MANUFACTURING_APPROVED → MANUFACTURING_STARTED | Подтверждение заказа из CRM не доходит до MES. Менеджер подтвердил заказ, но оператор его не видит. |
| 5 | MES внутренняя обработка | MANUFACTURING_STARTED → MANUFACTURING_COMPLETED | Оператор взял заказ, но статус не обновился из-за ошибки в MES. Или заказ «забыт» оператором — нет контроля таймаутов. |
| 6 | MES → RabbitMQ → CRM | SHIPPED → CLOSED | Уведомление об отправке не доходит до CRM. Заказ отправлен, но не закрывается в CRM. |
| 7 | B2B API → MES | Создание заказа через API | Внешний запрос не обрабатывается, теряется, или MES перегружен и не отвечает. B2B-клиент не получает подтверждения. |

### Данные, которые должны попадать в трейсинг

Для каждого span (единицы работы) в трейсе необходимо записывать:

**Обязательные атрибуты:**
- `trace_id` — уникальный идентификатор трейса, сквозной для всего жизненного цикла заказа
- `span_id` — идентификатор текущей операции
- `parent_span_id` — идентификатор родительской операции
- `service.name` — название сервиса (`online-shop`, `mes`, `crm`)
- `timestamp` — время начала и окончания операции
- `duration` — длительность операции
- `status` — результат операции (`OK`, `ERROR`)

**Бизнес-атрибуты:**
- `order.id` — идентификатор заказа
- `order.status` — текущий статус заказа
- `order.status_from` → `order.status_to` — переход статуса
- `order.source` — источник заказа (`b2c_website`, `b2b_api`)
- `customer.id` — идентификатор клиента (хешированный для безопасности)
- `order.total_price` — стоимость заказа (при расчёте)

**Технические атрибуты:**
- `http.method`, `http.url`, `http.status_code` — для HTTP-вызовов
- `messaging.system` = `rabbitmq` — для сообщений через очередь
- `messaging.destination` — имя очереди
- `messaging.operation` — `publish` / `consume`
- `db.system`, `db.statement` — для запросов к БД (без чувствительных данных)
- `error.message`, `error.stack_trace` — при ошибках
- `file.name`, `file.size` — при загрузке 3D-модели

## 2. Мотивация

### Почему в систему нужно добавить трейсинг

Сейчас команда не имеет возможности отследить путь заказа через три разных системы (Online Shop → MES → CRM), связанные асинхронно через RabbitMQ. Когда клиент жалуется, что заказ «потерялся», разработчикам приходится вручную проверять логи каждого сервиса, пытаясь восстановить картину. Это занимает часы и дни.

После открытия B2B API проблема усилилась: компания уже потеряла несколько крупных контрактов. Трейсинг позволит в реальном времени видеть, на каком этапе находится каждый заказ и где именно произошёл сбой.

### Технические и бизнес-метрики, на которые повлияет внедрение трейсинга

1. **MTTR (Mean Time to Resolve)** — среднее время устранения инцидента. Сейчас измеряется часами/днями, с трейсингом сократится до минут. Команда сможет мгновенно увидеть, в каком сервисе завис заказ и какая ошибка произошла.

2. **Количество потерянных заказов в месяц** — трейсинг позволит обнаруживать «застрявшие» заказы автоматически, до жалобы клиента. Цель — снижение на 90%+ за первые 3 месяца после внедрения.

3. **Customer Satisfaction (CSAT) / NPS** — прямое влияние через сокращение случаев «потерянных» заказов и ускорение разрешения проблем при обращении в поддержку.

4. **Среднее время обработки заказа (end-to-end)** — трейсинг покажет реальную картину: сколько времени заказ проводит в каждом сервисе. Это позволит выявить узкие места и оптимизировать процесс. Бизнес обещает клиентам 3 недели, но часть заказов обрабатывается месяцами.

5. **Количество обращений в поддержку по статусу заказа** — с внедрением трейсинга поддержка сможет самостоятельно проверять статус заказа без привлечения разработчиков. В перспективе — предоставить B2B-клиентам API для отслеживания статуса.

## 3. Предлагаемое решение

### 3.1. Выбор технологий

**OpenTelemetry** — как стандарт инструментирования. OpenTelemetry является vendor-neutral стандартом, поддерживается всеми основными языками (Java, C#, JavaScript) и позволяет менять бэкенд хранения трейсов без изменения кода приложений.

- **Java (Online Shop, CRM):** OpenTelemetry Java Agent — автоматическое инструментирование Spring Boot без изменений кода. Поддерживает Spring MVC, JDBC, RabbitMQ client «из коробки».
- **C# (MES):** OpenTelemetry .NET SDK — автоматическое инструментирование ASP.NET, HttpClient, ADO.NET. Для RabbitMQ — ручное инструментирование через OpenTelemetry API.

**Jaeger** — как бэкенд для хранения и визуализации трейсов. Выбор обоснован:
- Open-source, нет лицензионных расходов.
- Нативная поддержка OpenTelemetry (OTLP-протокол).
- Удобный UI для поиска трейсов по order_id, service name, статусу ошибки.
- Поддержка Elasticsearch как хранилища (масштабируемость).
- Активное сообщество и зрелость проекта (CNCF Graduated).

**OpenTelemetry Collector** — промежуточный компонент для приёма, обработки и экспорта телеметрии. Позволяет:
- Собирать трейсы от всех сервисов в едином формате.
- Фильтровать и обогащать данные перед отправкой в Jaeger.
- Семплировать трейсы при высокой нагрузке.
- Буферизировать данные при недоступности бэкенда.

### 3.3. Компоненты для внедрения и доработки

#### Новые компоненты (выделены красным на диаграмме):

1. **OpenTelemetry Collector** — отдельный сервис (EC2-инстанс или контейнер). Принимает телеметрию от всех приложений по OTLP/gRPC, обрабатывает и отправляет в Jaeger.

2. **Jaeger** — сервис для хранения, поиска и визуализации трейсов. Развёрнуть на отдельном EC2-инстансе. Компоненты: Jaeger Query (UI + API), Jaeger Collector (приём данных), Jaeger Ingester.

3. **Elasticsearch** (для хранения трейсов) — Managed Elasticsearch в Yandex Cloud. Хранение трейсов с индексацией по `trace_id`, `order_id`, `service.name`, `timestamp`. Политика хранения — 30 дней hot, 90 дней warm.

#### Доработка существующих компонентов:

4. **Online Shop API** — подключить OpenTelemetry Java Agent (через JVM-аргумент `-javaagent`). Добавить кастомные атрибуты: `order.id`, `order.status`, `customer.id`. Инструментировать RabbitMQ-клиент для propagation контекста.

5. **CRM API** — аналогично Online Shop: OpenTelemetry Java Agent + кастомные атрибуты. Инструментировать RabbitMQ consumer для извлечения trace context из headers сообщений.

6. **MES API** — подключить OpenTelemetry .NET SDK. Настроить автоинструментирование ASP.NET и ADO.NET. Ручное инструментирование для RabbitMQ (публикация trace context в headers сообщений). Особое внимание — span для длительного расчёта стоимости (2-30 мин).

7. **RabbitMQ** — обеспечить propagation trace context через message headers. При публикации сообщения сервис записывает `traceparent` и `tracestate` в headers, при потреблении — извлекает и продолжает трейс.

### 3.4. Пропагация контекста через RabbitMQ

Ключевой технический вызов — сохранение единого трейса при асинхронном взаимодействии через очередь:

```
Producer (MES):                          Consumer (CRM):
1. Создать span "publish_message"        1. Извлечь traceparent из headers
2. Inject trace context в headers:       2. Создать span "consume_message"
   - traceparent                            с parent = extracted context
   - tracestate                          3. Продолжить обработку
3. Отправить сообщение в RabbitMQ           в рамках того же трейса
```

Это позволит видеть полный путь заказа как единый трейс, даже через асинхронные переходы.

### 3.6. Автоматический мониторинг прохождения заказа и алертинг (дополнительное задание)

На основе данных трейсинга реализуем автоматический мониторинг жизненного цикла заказа:

#### Механизм

1. **Span Metrics Connector** в OpenTelemetry Collector — автоматически преобразует данные трейсинга в метрики (RED-метрики из span-данных). Экспортирует метрики в Prometheus.

2. **Prometheus** — хранит метрики, полученные из трейсов. Правила алертинга (alerting rules) проверяют условия:

3. **Alertmanager** — маршрутизирует алерты в Slack и PagerDuty.

#### Алерты на основе трейсинга

| Алерт | Условие | Реакция |
|-------|---------|---------|
| `OrderStuckInStatus` | Заказ находится в одном статусе дольше порога (SUBMITTED > 1 час, PRICE_CALCULATED > 30 мин, MANUFACTURING_APPROVED > 2 часа) | Тикет в трекере + уведомление в Slack. Поддержка проверяет заказ в Jaeger UI. |
| `OrderTraceGap` | Трейс заказа обрывается — нет span после определённого статуса в течение порогового времени | Критический алерт. PagerDuty → дежурный инженер. Вероятно, сообщение потеряно в RabbitMQ. |
| `HighOrderProcessingTime` | p95 end-to-end времени обработки заказа превышает SLA (например, 4 часа для стандартного расчёта) | Уведомление в Slack. Тикет на анализ узкого места. |
| `B2BOrderFailureRate` | Более 5% заказов от B2B-партнёра завершаются ошибкой за последний час | Уведомление менеджеру аккаунта + дежурному инженеру. |
| `PricingCalculationTimeout` | Расчёт стоимости занимает более 30 минут | Уведомление оператору MES + инженеру. |

#### Обновлённая архитектура (с алертингом)

```
OTel Collector ──(Span Metrics Connector)──► Prometheus ──► Alertmanager ──► Slack / PagerDuty
```

## 4. Компромиссы

### 4.1. Длительные операции MES (расчёт стоимости 2-30 минут)

Расчёт стоимости 3D-модели может длиться до 30 минут. Создание одного span на всю длительность расчёта нецелесообразно — это огромный span, который не даёт полезной информации о внутренних этапах. Однако MES — купленная система с исходным кодом, и глубокое инструментирование внутренних этапов расчёта потребует значительных усилий команды (один C#-разработчик).

**Решение-компромисс:** На первом этапе создаём один span `pricing_calculation` с атрибутами `model_complexity` (количество полигонов) и `duration`. Глубокое инструментирование — на втором этапе, когда команда лучше разберётся в коде MES.

### 4.2. Фронтенд-трейсинг

Полноценный трейсинг фронтенда (Vue для Online Shop и CRM, React для MES) потребует:
- Интеграции OpenTelemetry JS SDK в три разных фронтенд-приложения.
- Двух разных фреймворков (Vue + React) — удвоение усилий.
- Работы фронтенд-разработчиков, которых всего два (и один из них только частично знает React).

**Решение-компромисс:** На первом этапе покрываем трейсингом только бэкенд-сервисы. Фронтенд-трейсинг — после стабилизации бэкенд-трейсинга. Для фронтенда пока достаточно Яндекс Метрики и мониторинга HTTP-запросов на стороне API.

### 4.3. Overhead на производительность

OpenTelemetry добавляет overhead: создание span-объектов, сериализация, отправка по сети. Для MES, который и так испытывает проблемы с производительностью, это может быть критично.

**Решение-компромисс:** Настроить sampling (семплирование) в OpenTelemetry Collector:
- Для MES API: sampling rate 50% для обычных запросов, 100% для запросов с ошибками (tail-based sampling).
- Для Online Shop и CRM: sampling rate 100% на начальном этапе (нагрузка невысокая), снижать при росте.

### 4.4. Стоимость хранения трейсов

Хранение всех трейсов в Elasticsearch при растущей нагрузке будет стоить всё дороже. Каждый заказ генерирует десятки span-ов.

**Решение-компромисс:** Политика хранения:
- Hot storage (SSD): 30 дней — для оперативного анализа.
- Warm storage (HDD): 90 дней — для исторического анализа.
- Удаление после 90 дней (или архивирование в S3 для compliance).

### 4.5. Транспортная компания — внешняя система

Переход SHIPPED → CLOSED зависит от получения сообщения от транспортной компании. Это внешняя, неконтролируемая система, инструментирование которой невозможно. Трейс заказа будет «обрываться» на статусе SHIPPED.

**Решение-компромисс:** Зафиксировать span `awaiting_shipping_confirmation` с пометкой `external_dependency = true`. Мониторить время нахождения в этом статусе. Алертить при превышении ожидаемого срока доставки.

## 5. Безопасность

### 5.1. Аутентификация и авторизация доступа к Jaeger UI

- **Аутентификация:** Доступ к Jaeger UI только через корпоративную SSO (Single Sign-On) с использованием существующей системы аутентификации компании. Если SSO не настроен — через OAuth2 Proxy перед Jaeger UI.
- **Ролевая модель:**
  - Роль **«Поддержка»** — просмотр трейсов, поиск по order_id и customer_id. Доступ к Jaeger UI в режиме read-only.
  - Роль **«Разработчик»** — полный доступ к трейсам, включая технические атрибуты (stack traces, DB queries).
  - Роль **«Администратор»** — управление настройками Jaeger, политиками хранения, семплирования.
- **Разграничение:** Продавцы, операторы и внешние пользователи (B2B-партнёры) **не имеют доступа** к Jaeger UI. Информация о статусе заказа для них предоставляется через API приложений.

### 5.2. Сетевая безопасность

- Jaeger UI, OTel Collector и Elasticsearch размещаются в **приватной подсети** VPC, недоступной из интернета.
- Доступ к Jaeger UI — только через VPN или через корпоративный reverse proxy с аутентификацией.
- Трафик между сервисами и OTel Collector — по внутренней сети, шифрование через TLS (mTLS при необходимости).
- Трафик OTel Collector → Jaeger и Jaeger → Elasticsearch — также по внутренней сети с TLS.

### 5.3. Защита персональных данных в трейсах

- **customer_id** — хранить в виде хеша (SHA-256), а не в открытом виде. Маппинг hash → real_id доступен только через CRM с соответствующими правами.
- **Запрет записи PII** (Personally Identifiable Information) в span-атрибуты: имя клиента, email, телефон, адрес доставки **не должны** попадать в трейсинг.
- **Фильтрация в OTel Collector:** Настроить processor `attributes` для удаления или маскирования чувствительных данных до отправки в Jaeger.
- **DB statements:** Записывать только тип запроса и таблицу, без значений параметров (могут содержать PII).
